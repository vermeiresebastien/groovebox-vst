# Doc line ranges whose citations are deliberately NOT renumbered, with the reason.
#
# cite-sweep.py reads this twice: it skips these lines when deciding what to shift, and it
# *restores* them when the shift has already happened -- a line whose text differs from
# HEAD's only in digits is written back as HEAD wrote it. Restoring rather than leaving is
# the point: a mechanically shifted number looks verified, and these do not deserve that.
#
# Three reasons appear here, and they are not all the same job:
#
#   pinned    -- the doc section names its own baseline commit, so its numbers are correct
#                *for that tree* and moving them would falsify the record;
#   unverified -- cite-audit.py can name the symbol in the sentence and cannot find it
#                at the lines the citation gives, so the map cannot answer it. Measured
#                against `460b3bf` afterwards, 13 of the 15 were RIGHT where they were
#                written and only went stale later, and the rest were wrong the day they
#                were typed -- which is the other half of why a map cannot fix them: a
#                shift preserves what HEAD's number pointed at, wrong or not. They stay at
#                HEAD's text and the finding -- where each symbol actually lives now -- is
#                a tracked item in NEXT-STEPS.md 6.6, which 6.7 closed by moving this
#                folder out of gitignored `out/`.
#   repaired  -- the first two hold a line *at* the baseline; this one holds it *away* from the
#                baseline, and the sweep must not restore. The base's number was wrong the day it
#                was written, and renumbering it faithfully moves the error along with everything
#                else: `bcd6188`'s `PluginProcessor.h:256-261` is `envelopeSecondsFor` and
#                `formatEnvelopeValue`, not the `parameterChanged` doc comment the sentence is
#                quoting, and `PluginProcessor.cpp:772-961` opens in the middle of
#                `loadSampleIntoChannel`, not in the base64 codec. Both were fixed by reading the
#                tree, and both are still in the sentence's own item -- so an `unverified` pin
#                would have put the wrong number back on the next pass. The working copy's number
#                is what stays. `cite-sweep.py` skips them and prints them as held, and
#                `cite-audit.py` *judges* them rather than excepting them: a repair is a claim
#                about this tree, and this is the only tool that can check one. Verified 2026-11-16
#                against the working tree -- `parameterChanged` is declared at
#                `Source/PluginProcessor.h:612`, its comment opening at 602; the encode is
#                `juce::Base64::toBase64` at `Source/PluginProcessor.cpp:1350` and the decode
#                `convertFromBase64` at 1435, both inside 1245-1526. The line beside the first
#                repair, `PluginProcessor.cpp:92,97` in the same B5 item, is deliberately left
#                `unverified` above: reading those two substring calls costs a rewrite of what the
#                item claims, which is plan 6.6's, not 14a's.
#
# Format: <doc> <first>-<last>   # <reason>
#
# base: bcd6188
#
# The numbers are coordinates in the commit named on the `base:` line above, never in HEAD.
# That distinction was earned the hard way, in the same sitting as the 4.4 commit: both scripts
# read their baseline with `git show HEAD:`, so the moment this lane committed its own docs the
# same commands over the same tree answered `122 already right, 2 to correct / UNPINNED miss: 13`
# instead of `43, 0, 0 / miss: 0` -- the pins had silently re-scoped to a different slice, and
# thirteen of the fifteen `unverified` entries fell out of their own ranges. A baseline you cannot
# re-check is an opinion, and `HEAD` is not one you can: it moves under the commit that documents
# it. Advance `base:` deliberately, in the same pass that re-checks every range below it, and the
# run prints which base it used so a stale one is visible rather than merely wrong.
#
# The working-copy side is matched by masked text, not by index, because the docs grow: editing
# this file above a pinned line shifts every number below it, and a range taken as a working-copy
# index would then pin the wrong paragraph -- a plausible one, since documents of this shape
# repeat themselves.
